# AI 小说情感深度解决方案

> 解决核心痛点：AI 输出文本缺乏情感深度，内容程式化、按部就班，无法生成具有强烈情感表达力和文学感染力的文字。
>
> 参考项目：[webnovel-writer](https://github.com/lingfengQAQ/webnovel-writer)（lingfengQAQ）、[PlotPilot](https://github.com/shenminglinyi/PlotPilot)（shenminglinyi）
>
> 本方案基于对上述两个项目的源码级分析，结合你现有 FastAPI + SQLite 项目的实际架构，给出可落地的系统性改进路径。

---

## 一、问题诊断：为什么 AI 写的小说"程式化"

在动手设计前，必须先找准根因。AI 小说之所以读起来"按部就班、缺乏情感深度"，不是模型不够强，而是**整个生成管线把情感当成了"模型自由发挥的副产物"，而不是"被显式建模、传递、注入、审查的一等公民"**。

具体表现为五个断点：

| 断点 | 表现 | 后果 |
|------|------|------|
| **情感无状态** | 角色当下的情感状态没有被建模和持久化 | 上一章愤怒，本章突然平静，无过渡 |
| **情感无规划** | 写正文前没有"本章要达成什么情感效果"的蓝图 | 情感靠运气，平铺直叙是默认结果 |
| **指令无情感** | system prompt 只说"参考记忆、角色、大纲"，不说"达成什么情感张力" | 模型把"写完"当目标，而非"写得有感染力" |
| **审查无情感** | 审查只查事实一致性、雷点，不查情感深度、潜台词、氛围 | 情感质量零反馈，无法迭代改进 |
| **模式无回流** | 拆解好作品得到的"情绪链条、爽感条件"只停留在拆书阶段，不回流到写作 | 学了等于没学 |

你现有项目里这五个断点都存在。最有力的证据就在 `main.py`：

- `build_local_chapter_draft` 这个本地 stub 其实写得相当有文学性——"雨声贴着灰塔外墙往上爬，像有人在玻璃背后用指节轻敲"，有意象、有压力、有选择。但这套写法是**硬编码**的，完全没有进入 prompt 系统。
- `system_prompt_for_workflow` 对正文生成的全部指令是"必须参考记忆、角色、大纲、时间线、伏笔、雷点……避免重复"——**通篇是"约束"，没有一句"情感目标"**。
- `character-profiles` 的 payload 里有 `voice` 字段（"短句、克制、少用感叹"），但生成时**根本没把这个字段映射到对话生成的指令里**。

这就是程式化的技术根源。解决方案的总思路，就是把上面五个断点逐个接上。

## 二、两个参考项目的情感表达机制剖析

### 2.1 webnovel-writer（lingfengQAQ）

**定位**：基于 Claude Code 的长篇网文辅助创作插件，主打"写到 200 万字仍记得住设定、接得住伏笔"的一致性系统。

**与情感相关的机制**：

1. **Strand Weave 节奏系统**——把内容分三条线：Quest（主线 60%）、Fire（感情线 20%）、Constellation（世界观 20%），并设断档红线（Fire 断档不超过 10 章）。这是**节奏维度**的粗粒度控制，保证感情线不会长期消失，但不规定"感情怎么写"。

2. **deconstruction-agent（拆文 agent）**——这是整个分析中最接近"情感模式提取"的机制。它会：
   - 把参考文本拆成"信息团"，每个信息团标注**情绪上行/下行/转折**；
   - 抽离**条件框架**——"什么条件组合造成爽感/期待/反差"，而不是复制具体桥段；
   - 记录主角压力模型、反派层级、爽点循环（铺垫→释放→反应层→衔接）。

   **但致命问题在于**：这套拆解产出只用于 `/webnovel-init` 阶段生成"候选创意约束包"，**完全不回流到 `/webnovel-write` 的写作阶段**。拆出来的"情绪链条"从未进入正文生成的上下文。这是最大的浪费。

3. **reviewer 六维审查**——架构文档宣称含"爽点、追读力"，但实际 `reviewer.md` 明确声明："不评分、不评价文笔质量——'写得不够好'不是 issue，'与角色性格矛盾'才是"。审查的五维度（设定/时间线/连贯/角色/逻辑）**全是事实层**。爽点和追读力在另一条 pipeline，但同样是"钩子强度"这种网文指标，不是"情感深度"。

4. **追读力系统**（Hook / Cool-point / 微兑现 / 债务追踪）——这是网文向的"爽感工程"，关注的是"读者会不会追下一章"，而非"这段文字有没有情感感染力"。两者有交集但不等同。

**优势**：合同驱动（Story System）的事实治理极其扎实；拆文 agent 的"条件框架"思路非常先进；Strand 比例红线对长篇节奏有约束力。

**不足**：拆文成果不回流；审查明确排斥文笔质量；情感维度全程缺位；"爽点"替代了"情感深度"。

### 2.2 PlotPilot（shenminglinyi）

**定位**：开源剧情引擎内核（Narrative Engine Kernel），通过 REST API 暴露能力，采用 DDD 分层架构。

**与情感相关的机制**：

1. **张力心电图（Tension ECG）**——每章生成后计算张力评分（0-10），历史曲线持久化，低谷自动触发诊断。这是**事后评估**，且"张力"更接近"戏剧冲突强度"，不完全等于"情感深度"。

2. **文风相似度检测 + 漂移告警**——基于向量余弦相似度计算与风格基准的偏离，偏离超阈值触发**定向修写**（不回滚，保留进度渐进治理）。这个思路很好，但"文风"是整体风格，不是"情感浓度"。

3. **陈词滥调扫描**——规则库 + 语义相似度双重检测高频套路表达。这是**消极防御**（去掉 AI 味），不是**积极建设**（注入文学性）。

4. **叙事治理预算**——章节生成前分配"叙事预算"，属于结构层规划，不含情感预算。

5. **20+ 独立提示接点**——`scene-director`、`chapter-narrative-sync` 等接点可通过 YAML 独立覆写。架构上为情感注入留了扩展位，但默认提示包里没有显式的情感指令。

**优势**：DDD 分层 + 十步管线的工程化程度极高；张力心电图实现了"评分-诊断-修写"闭环；定向修写（不回滚）的渐进治理理念先进；提示接点解耦，可独立覆写。

**不足**：所有质量机制都是**事后**的（写完才评分/检测）；没有情感状态建模；没有情感前置规划；"张力"和"文风"都不能等同于"情感深度"。

### 2.3 共同盲区总结

两个项目在"一致性"和"质量治理"上各有建树，但在"情感深度"上共享同一个结构性缺陷：

| 维度 | webnovel-writer | PlotPilot | 共同问题 |
|------|----------------|-----------|---------|
| 情感状态 | 无 | 无 | 角色情感不被建模为一等公民 |
| 情感规划 | Strand 比例（粗） | 叙事预算（无情感） | 写前没有"情感目标蓝图" |
| 情感注入 | prompt 无情感指令 | prompt 接点预留但默认空 | 生成时情感零输入 |
| 情感审查 | 明确排斥文笔 | 张力/文风（间接） | 没有情感深度专项审查 |
| 模式回流 | 拆文有模式但不回流 | 无拆文 | 好作品的情感模式无法复用 |

**一句话总结**：两个项目都把"不写崩"做到了系统级，但"写得有情感深度"几乎完全甩给模型自由发挥。这就是程式化的根源，也正是本方案要解决的核心。

## 三、系统化解决方案总览

### 3.1 核心理念

> **把情感从"模型自由发挥的副产物"升级为"被显式建模、传递、注入、审查的一等公民"。**

实现路径是建立一条与"事实治理链"并行的**"情感治理链"**：

```
事实治理链（你已有 + 两项目都强）：
  大纲/设定/伏笔 → 上下文装配 → 生成 → 事实审查 → 提交入库

情感治理链（本方案新增）：
  情感蓝图 → 情感上下文装配 → 情感驱动生成 → 情感质量审查 → 情感状态沉淀
```

两条链并行运转、共享上下文，但职责分离：事实链保证"不写崩"，情感链保证"写得动人"。

### 3.2 方案与四个痛点的映射

| 你的痛点 | 对应方案模块 | 所在章节 |
|---------|------------|---------|
| ① 叙述文本缺乏情感张力和文学性 | 情感蓝图 + 文学技法注入层 + 情感强化改写 | 第四章 |
| ② 角色对话缺乏真实细腻的情感 | 角色情感状态机 + 对话三层结构 + voice 映射 | 第五章 |
| ③ 情节推进缺乏情感氛围和节奏 | 情感节奏曲线 + 情感氛围场 + 张力闭环 | 第六章 |
| ④ 结合两项目的架构改进 | 借鉴点 + 关键改进 + 落地路径 | 第七章 |

### 3.3 与现有架构的融合原则

本方案**不另起炉灶**，而是在你现有的 FastAPI + SQLite 架构上扩展：

- 复用现有的 `build_generation_context` 上下文装配机制，扩展加入情感字段；
- 复用现有的 `run_ai_workflow` 工作流路由，新增情感相关工作流；
- 复用现有的 generic record 机制（character-profiles / style-profiles 等），扩展 payload；
- 复用现有的 wiki 同步机制，情感产物也沉淀为可检索记忆。

## 四、维度一：叙述文本的情感张力与文学性

**目标**：让 AI 生成具有情感张力和文学感染力的叙述，而非机械式平铺直叙。

### 4.1 情感蓝图（Emotion Blueprint）——写前规划

在 `generate_chapter_brief`（章节大纲）之后、`generate_chapter_draft`（正文）之前，**新增一个工作流 `generate_emotion_blueprint`**，为每章生成结构化的情感蓝图。

**情感蓝图的数据结构**：

```json
{
  "chapter_id": "...",
  "emotional_arc": {
    "shape": "rise-fall-rise | fall-rise | spiral | plateau-break",
    "start_valence": "不安",
    "peak_emotion": "被背叛的清醒",
    "end_valence": "压抑的决意",
    "valence_trajectory": [
      {"beat": "开场", "emotion": "不安", "intensity": 3, "direction": "neutral"},
      {"beat": "发现", "emotion": "震惊", "intensity": 7, "direction": "up"},
      {"beat": "对峙", "emotion": "愤怒", "intensity": 9, "direction": "up"},
      {"beat": "代价", "emotion": "空洞", "intensity": 5, "direction": "down"},
      {"beat": "决意", "emotion": "压抑的清醒", "intensity": 6, "direction": "up"}
    ]
  },
  "emotional_anchors": [
    {"position": "开场", "anchor": "雨声贴墙", "sensory_channel": "听觉", "emotion": "不安"},
    {"position": "高潮", "anchor": "裂开的印章", "sensory_channel": "视觉", "emotion": "被背叛"}
  ],
  "sensory_motifs": ["雨声", "冷光", "墨迹", "电梯数字"],
  "literary_techniques": [
    {"technique": "通感", "target_beat": "开场", "example_hint": "把雨声写成指节敲玻璃"},
    {"technique": "具象化情绪", "target_beat": "高潮", "example_hint": "用胸口被拧紧代替'心痛'"},
    {"technique": "留白", "target_beat": "代价", "example_hint": "不写她哭，写她擦桌子的动作"}
  ],
  "show_dont_tell_constraints": [
    "禁止出现'她很伤心/愤怒/害怕'类直陈情绪词",
    "情绪必须通过动作、感官、环境投射"
  ]
}
```

**关键设计点**：

- **`valence_trajectory`（情感轨迹）**：把一章拆成 4-6 个情感节拍，每个节拍有明确的情绪、强度（1-10）、方向（上行/下行/平稳）。这是给模型的"情感地图"，生成时必须沿这条轨迹走。
- **`emotional_anchors`（情感锚点）**：每个关键节拍绑定一个感官锚点（意象），让抽象情绪有具象载体。这正是你 stub 里"雨声贴墙"那种写法的系统化。
- **`literary_techniques`（文学技法）**：显式指定本章要用哪些技法（通感、具象化、留白、对比、意象复现……），并给出应用位置和示例提示。
- **`show_dont_tell_constraints`**：硬约束，禁止直陈情绪词，强制"展示而非讲述"。

**这是对 webnovel-writer 拆文 agent 的关键改进**：拆文得到的"情绪链条/条件框架"不再只停留在 init 阶段，而是转化为每章的 `emotional_arc` 和 `literary_techniques`，**回流到正文生成的上下文**。

### 4.2 文学技法注入层——改造 system prompt

你现有的 `system_prompt_for_workflow` 对正文生成的指令是纯约束式的。改造为**约束 + 情感指令**双轨：

```python
def system_prompt_for_workflow(workflow, emotion_blueprint=None):
    if workflow in {"generate_chapter_draft", "revise_selection"}:
        base = (
            "你是专业的中文长篇小说创作助手。当前任务是生成或改写小说正文。"
            "只返回可直接放入章节编辑器的中文正文，不要返回 JSON、Markdown 标题。"
            "必须参考上下文中的记忆、角色、大纲、时间线、伏笔、雷点。"
            "尤其要读取 volume_memory 和 anti_repetition_notes，避免重复。"
        )
        if emotion_blueprint:
            arc = emotion_blueprint["emotional_arc"]
            techs = emotion_blueprint.get("literary_techniques", [])
            constraints = emotion_blueprint.get("show_dont_tell_constraints", [])
            emotion_directive = (
                f"\n\n【情感蓝图·必须执行】\n"
                f"本章情感弧线形状：{arc['shape']}，起点{arc['start_valence']}，"
                f"高潮{arc['peak_emotion']}，终点{arc['end_valence']}。\n"
                f"情感节拍轨迹（按顺序达成，每段文字的情绪强度必须匹配）：\n"
                + "\n".join(
                    f"  · {b['beat']}：情绪={b['emotion']}，强度={b['intensity']}/10，方向={b['direction']}"
                    for b in arc["valence_trajectory"]
                )
                + "\n\n【感官锚点·必须命中】\n"
                + "\n".join(
                    f"  · {a['position']}：用{a['sensory_channel']}通道的'{a['anchor']}'承载'{a['emotion']}'"
                    for a in emotion_blueprint.get("emotional_anchors", [])
                )
                + "\n\n【文学技法·必须使用】\n"
                + "\n".join(
                    f"  · {t['technique']}（用于{t['target_beat']}）：{t['example_hint']}"
                    for t in techs
                )
                + "\n\n【硬约束】\n"
                + "\n".join(f"  · {c}" for c in constraints)
            )
            return base + emotion_directive
        return base
    # ... 其他 workflow 不变
```

**这段改造的本质**：把情感从"模型自己看着办"变成"蓝图里写清楚，prompt 里强制执行"。

### 4.3 情感强化改写——生成后的二次提纯

借鉴 PlotPilot 的"定向修写而非回滚"理念，在正文生成后增加一个 `emotional_intensify` 工作流。它不是全篇重写，而是：

1. 识别正文里**情感强度低于蓝图要求**的段落（与 `valence_trajectory` 对比）；
2. 对这些段落做**定向情感强化改写**——注入感官细节、把直陈情绪改写为具象呈现、强化节奏（短句制造紧张、长句铺陈压抑）；
3. 保留其他段落不动。

这比全篇重写成本低、风险小，且符合"渐进治理"理念。

## 五、维度二：角色对话的情感层次

**目标**：让角色对话真实、细腻、有层次，而非"信息传递工具人"。

### 5.1 角色情感状态机——给角色一个"当下的心"

你现有的 `character-profiles` 有 `voice` 字段，但它是**静态的**（"短句、克制、少用感叹"）。真实的人在对话时，语气会随当下情感状态变化——愤怒时克制的人也可能爆发，恐惧时话多的人也会结巴。

**扩展 character-profiles 的 payload，增加情感维度**：

```json
{
  "name": "沈照夜",
  "voice": "短句、克制、少用感叹",
  "emotional_baseline": {
    "default_emotion": "警惕性克制",
    "emotional_range": ["冷静", "压抑的愤怒", "被触动的动摇", "决绝"],
    "trigger_map": {
      "被质疑动机": "压抑的愤怒 → 短句变碎句",
      "提及旧朝": "动摇 → 句子出现停顿",
      "同伴受威胁": "决绝 → 放弃克制，使用祈使句"
    },
    "defense_mechanism": "用反问挡回直白情绪",
    "unspoken_rules": "从不说'我害怕'，只说'这事先放着'"
  },
  "current_emotional_state": {
    "emotion": "压抑的愤怒",
    "intensity": 6,
    "recent_trigger": "第12章被顾临舟隐瞒证词",
    "updated_at": "第12章末"
  }
}
```

**`current_emotional_state` 是动态字段**，每章写完后由 `extract_emotional_state` 工作流从正文反推并更新。这样下一章生成对话时，角色带着上一章的情感后遗症入场。

### 5.2 对话三层结构——字面 / 意图 / 潜台词

程式化对话的典型特征是"字面意思 = 真实意图"。真实的好对话永远有**潜台词层**——角色说的和想的不是一回事。

新增工作流 `generate_dialogue_with_subtext`，或在正文生成的 prompt 中注入对话三层约束：

```
【对话生成约束·三层结构】
每段对话必须同时满足：
1. 字面层（surface）：角色实际说的话，符合其 voice 和当下情感状态
2. 意图层（intent）：角色说这句话想达成什么（试探/施压/回避/索取确认）
3. 潜台词层（subtext）：角色真正在想的，但绝不会说出口的

要求：
- 字面层和潜台词层必须有张力（可以是反差、可以是呼应）
- 潜台词通过动作、停顿、环境细节暗示，绝不直接写出
- 角色的 current_emotional_state 决定字面层与潜台词层的距离：
  · 情绪强度低（1-3）：两层接近，潜台词浅
  · 情绪强度中（4-6）：两层有距离，潜台词明显
  · 情绪强度高（7-10）：两层可能完全相反（嘴上说"没事"，动作在发抖）
```

**示例**（基于你 stub 里的角色）：

> 字面：「你确定要进去？」守夜人问。
> 意图：劝退，试探她的决心。
> 潜台词：我不想再为别人的决定承担后果。
>
> 字面：「如果答案已经在里面等我，我不进去，它也会出来找我。」
> 意图：表明不可阻挡。
> 潜台词：我害怕，但害怕已经不重要了。

### 5.3 voice 到生成的映射——把静态设定激活

你现有项目最大的浪费之一：`voice` 字段存了但生成时没用。改造 `build_generation_context`，把角色的 voice + emotional_baseline + current_emotional_state 一起注入上下文，并在 prompt 里明确指示：

```
【角色对话风格·必须遵守】
沈照夜 当前情感状态：压抑的愤怒（强度6/10，因第12章被隐瞒证词）
- voice 基线：短句、克制、少用感叹
- 当前状态对 voice 的影响：短句会变碎句，克制会出现裂缝（偶尔一个不完整的感叹）
- 防御机制：用反问挡回直白情绪
- 禁忌：从不说"我害怕"，只说"这事先放着"
```

这样模型生成的对话，会带着角色"当下的情绪温度"，而不是永远用同一个腔调说话。

## 六、维度三：情节推进的情感氛围与节奏

**目标**：在情节推进中营造情感氛围，控制情感节奏的起伏变化。

### 6.1 情感节奏曲线——从套话到结构化节拍

你现有 `generate_chapter_brief` 的 `emotional_rhythm` 字段目前是套话（"以X带来的不安开场，中段升高外部压力，结尾留下具体代价"）。把它升级为**结构化的情感节拍序列**，与第四章的 `emotional_arc.valence_trajectory` 对齐：

```json
"emotional_rhythm": {
  "chapter_tension_target": 7,
  "beats": [
    {"order": 1, "name": "开场", "tension": 3, "pace": "慢", "mode": "氛围铺陈", "duration_ratio": 0.15},
    {"order": 2, "name": "异变", "tension": 5, "pace": "渐快", "mode": "信息注入", "duration_ratio": 0.20},
    {"order": 3, "name": "对峙", "tension": 8, "pace": "急促", "mode": "冲突爆发", "duration_ratio": 0.30},
    {"order": 4, "name": "代价", "tension": 4, "pace": "骤停", "mode": "情感沉淀", "duration_ratio": 0.20},
    {"order": 5, "name": "钩子", "tension": 6, "pace": "回升", "mode": "悬念植入", "duration_ratio": 0.15}
  ],
  "cross_chapter_arc": {
    "previous_end_tension": 5,
    "this_chapter_delta": "+2",
    "next_chapter_setup": "本章钩子要在下一章前3段兑现"
  }
}
```

**关键改进**：

- `tension`（1-10）是每个节拍的张力目标，生成时正文在该节拍的冲突密度必须匹配；
- `pace`（慢/渐快/急促/骤停/回升）控制句式节奏——慢=长句铺陈，急促=短句密集，骤停=单句独段；
- `duration_ratio` 控制每个节拍的篇幅占比，防止"高潮一笔带过、铺垫冗长"；
- `cross_chapter_arc` 让节奏跨章连续，避免每章都从零开始。

### 6.2 情感氛围场——场景级的情感基调

节奏是时间维度的，氛围是空间/场景维度的。每个场景应该有自己的**情感氛围场**：

```json
"atmosphere_fields": [
  {
    "scene": "档案层入口",
    "mood": "压抑的等待",
    "dominant_senses": ["听觉-雨声", "触觉-湿冷", "视觉-冷光"],
    "environmental_emotion_projection": "门禁屏幕的滚动字 = 时间压力的具象化",
    "pacing_speed": "慢",
    "color_palette_hint": "灰、冷白、墨黑"
  },
  {
    "scene": "抽屉发现签名",
    "mood": "被背叛的清醒",
    "dominant_senses": ["触觉-指腹停 in墨迹", "听觉-机器吞吐纸页"],
    "environmental_emotion_projection": "无编号抽屉 = 失序的隐喻",
    "pacing_speed": "急促",
    "color_palette_hint": "暗黄、裂痕"
  }
]
```

**氛围场的价值**：让"环境"不再只是背景板，而是情感的**投射载体**。雨声不是装饰，是不安的具象；冷光不是描写，是疏离的载体。这正是你 stub 里已经无意识做到的写法，现在要系统化。

### 6.3 张力闭环：规划 → 生成 → 校验

借鉴 PlotPilot 的张力心电图，但把它从"事后评估"升级为"事前规划 + 事后校验"的完整闭环：

```
事前：emotional_rhythm.beats[].tension  →  生成时正文必须达到该张力
事中：生成时按 beats 的 pace/duration_ratio 控制节奏
事后：analyze_emotional_quality 工作流  →  逐节拍校验实际张力 vs 目标张力
反馈：偏差 > 阈值  →  触发 emotional_intensify 定向修写（不回滚）
沉淀：实际张力曲线入 emotional_state_history，供下一章 cross_chapter_arc 参考
```

这是对 PlotPilot"张力心电图"的关键升级：PlotPilot 是"写完打分→低谷诊断"，本方案是"写前定标→写中执行→写后校验→偏差修写→沉淀历史"的完整 PDCA 闭环。

## 七、维度四：结合两项目的架构改进

### 7.1 从 webnovel-writer 借鉴什么

| 借鉴点 | 原项目做法 | 本方案改进 |
|--------|-----------|-----------|
| **Story System 合同驱动** | 写前合同 + 写后提交，事实可审计 | 把"情感蓝图"纳入合同：写前生成 blueprint 作为情感合同，写后提交实际情感轨迹作为情感 commit |
| **deconstruction-agent 拆文** | 拆参考书得"情绪链条/条件框架"，但只用于 init | **核心改进：让拆文成果回流**——把"爽感条件""情绪上行下行模式"转化为可复用的 emotional_pattern_library，每章生成 blueprint 时从中匹配调用 |
| **Strand Weave 节奏** | Quest/Fire/Constellation 比例红线 | 保留比例红线，但 Fire（感情线）不再是"有没有写感情线"的二元判断，而是"感情线的情感强度是否达标"的量化判断 |
| **六维审查** | 事实层五维 + 追读力 | 扩展为"事实五维 + 情感三维"：新增 emotional_depth / subtext_richness / atmosphere_consistency |

### 7.2 从 PlotPilot 借鉴什么

| 借鉴点 | 原项目做法 | 本方案改进 |
|--------|-----------|-----------|
| **十步管线** | 规划→上下文→生成→验证→漂移检测→章末→索引→张力→落库 | 在"上下文装配"后插入"情感蓝图装配"，在"生成"后插入"情感强化"，在"张力评分"处升级为"情感质量审查闭环" |
| **张力心电图** | 事后打分 + 低谷诊断 | 升级为事前规划+事后校验闭环（见 6.3） |
| **定向修写（不回滚）** | 文风漂移触发定向修写 | 扩展为"情感偏差触发定向修写"——只改情感不达标的节拍，保留其他 |
| **提示接点解耦** | 20+ YAML 可独立覆写 | 采用相同思路：情感相关指令也做成可覆写的提示片段（emotion_directive / dialogue_directive / atmosphere_directive） |
| **陈词滥调扫描** | 规则库 + 语义相似度 | 扩展为"情感套路扫描"——不只查"陈词滥调"，还查"情感虚假信号"（如滥用感叹号、情绪转折无铺垫、潜台词缺失） |

### 7.3 关键改进点总结（两项目都没做到的）

1. **情感状态建模**——两项目都没有。本方案给每个角色建 `current_emotional_state`，跨章持续。
2. **情感前置规划**——两项目都是事后评估。本方案写前生成 emotional_blueprint，情感目标是输入而非输出。
3. **拆文模式回流**——webnovel-writer 拆了但不用。本方案建 emotional_pattern_library，让好作品的情感模式可复用。
4. **情感专项审查**——两项目审查都不含情感深度。本方案新增三维情感审查。
5. **对话潜台词层**——两项目都没处理。本方案强制对话三层结构。
6. **氛围场建模**——两项目都把环境当背景。本方案把环境作为情感投射载体建模。

## 八、落地实施路径

### 8.1 数据模型扩展（database.py）

新增三张表（复用现有 generic record 模式）：

```sql
-- 章节情感蓝图（每章一条，写前生成）
CREATE TABLE chapter_emotion_blueprints (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    chapter_id TEXT NOT NULL,
    blueprint_json TEXT NOT NULL,  -- 第四章的完整结构
    status TEXT DEFAULT 'draft',   -- draft / approved / executed
    created_at TEXT, updated_at TEXT
);

-- 角色情感状态（每角色每章一条，写后沉淀）
CREATE TABLE character_emotional_states (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    character_id TEXT NOT NULL,
    chapter_id TEXT NOT NULL,
    emotion TEXT, intensity INTEGER,
    trigger TEXT, subtext_hint TEXT,
    created_at TEXT
);

-- 情感模式库（从拆文沉淀，可复用）
CREATE TABLE emotional_pattern_library (
    id TEXT PRIMARY KEY,
    project_id TEXT,
    source TEXT,  -- 拆文来源 / 手动录入
    pattern_name TEXT,
    condition_framework TEXT,  -- 什么条件组合造成什么情感效果
    applicable_genres TEXT,
    pattern_json TEXT,
    usage_count INTEGER DEFAULT 0,
    created_at TEXT
);
```

同时扩展 `character-profiles` 和 `chapter_versions` 的 payload，加入情感字段（无需改表结构，payload 是 JSON）。

### 8.2 工作流扩展（main.py 的 run_ai_workflow）

在现有工作流基础上新增五个：

| 新工作流 | 时机 | 作用 |
|---------|------|------|
| `generate_emotion_blueprint` | chapter_brief 之后、draft 之前 | 生成章节情感蓝图 |
| `generate_dialogue_with_subtext` | draft 中含对话时 | 对话专项生成（三层结构） |
| `emotional_intensify` | draft 之后 | 定向情感强化改写 |
| `extract_emotional_state` | 章节定稿时 | 从正文反推角色情感状态并沉淀 |
| `analyze_emotional_quality` | 审查阶段 | 三维情感质量审查 |

`build_generation_context` 扩展，加入 `emotion_blueprint`、`character_emotional_states`、`emotional_pattern_library` 三个字段。

### 8.3 Prompt 工程重构

把现在单一的 `system_prompt_for_workflow` 拆成**可组合的提示片段**（借鉴 PlotPilot 的接点思路）：

```
base_constraint_directive   （事实约束，现有）
emotion_blueprint_directive （情感蓝图指令，新增）
dialogue_subtext_directive  （对话潜台词指令，新增）
atmosphere_field_directive  （氛围场指令，新增）
anti_cliché_directive       （反套路指令，增强现有）
```

不同工作流按需组合。例如 `generate_chapter_draft` = base + emotion + dialogue + atmosphere + anti_cliché。

### 8.4 审查闭环建设

现有 `score_chapter` 只有一个总分。扩展为多维度评分：

```json
{
  "fact_consistency": 85,      // 现有事实一致性
  "emotional_depth": 72,       // 情感深度（蓝图达成度 + 潜台词丰富度）
  "atmosphere_consistency": 78,// 氛围场达成度
  "subtext_richness": 68,      // 对话潜台词层次
  "cliché_risk": 15,           // 套路风险（越低越好）
  "total": 76,
  "weak_beats": [
    {"beat": "对峙", "target_tension": 8, "actual_tension": 5, "issue": "冲突未充分爆发，情绪转折缺铺垫"}
  ],
  "revise_suggestion": "对第3节拍做 emotional_intensify"
}
```

`weak_beats` 直接驱动 `emotional_intensify` 的定向修写。

### 8.5 分阶段实施计划

| 阶段 | 内容 | 预期收益 |
|------|------|---------|
| **P0（1-2天）** | system_prompt 注入情感指令 + character voice 激活 | 立竿见影，对话和叙述立刻有情感方向 |
| **P1（3-5天）** | generate_emotion_blueprint 工作流 + 情感蓝图入上下文 | 写前有情感目标，告别平铺直叙 |
| **P2（3-5天）** | character_emotional_states 表 + extract_emotional_state | 角色情感跨章连续 |
| **P3（2-3天）** | analyze_emotional_quality 三维审查 + weak_beats 驱动修写 | 情感质量可量化、可迭代 |
| **P4（3-5天）** | emotional_pattern_library + 拆文回流 | 好作品情感模式可复用 |
| **P5（可选）** | 氛围场建模 + 对话潜台词专项工作流 | 进阶文学性 |

建议从 P0 开始——改动最小（只改 prompt），但效果最直接。先让你感受到"情感指令化"的威力，再逐步建设完整链路。

## 九、预期效果与风险

### 9.1 预期效果

- **叙述文本**：从"平铺直叙完成情节"变为"沿情感轨迹推进，有感官锚点和文学技法"；
- **角色对话**：从"信息传递工具人"变为"带着当下情绪温度、有潜台词层次的真实对话"；
- **情节节奏**：从"靠感觉"变为"按节拍张力曲线可控起伏，跨章连续"；
- **质量可迭代**：情感从"不可言说的玄学"变为"可评分、可定位薄弱节拍、可定向修写"的工程对象。

### 9.2 风险与对策

| 风险 | 对策 |
|------|------|
| 情感蓝图本身程式化（套话蓝图） | emotional_pattern_library 提供多样模板；蓝图生成时强制要求具体感官锚点而非抽象情绪词 |
| 过度指令导致模型僵硬 | 指令给"目标 + 约束"，不给"具体句子"；保留模型发挥空间；emotional_intensify 只改薄弱节拍 |
| 潜台词层失控（模型直接写出潜台词） | prompt 硬约束"潜台词通过动作暗示，绝不直接写出"；审查层检测直陈情绪词 |
| 情感状态维护成本 | extract_emotional_state 复用现有定稿流程，不增加额外人工步骤 |
| token 成本上升 | 情感蓝图复用 compact 机制（你已有 trim_text/compact_value）；对话潜台词指令只在含对话段落触发 |
